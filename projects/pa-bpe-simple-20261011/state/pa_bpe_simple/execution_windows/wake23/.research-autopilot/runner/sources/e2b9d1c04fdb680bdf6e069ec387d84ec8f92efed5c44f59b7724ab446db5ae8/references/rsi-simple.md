# One method: evidence, action, feedback

This is the default contract of the `rsi-simple` edition. Use the existing method
and the next decision to choose work. Read only relevant full-workflow modules
when their techniques help; importing a technique does not import its old global
admission gates. Do not run a paper-readiness campaign to debug one formula.
For research objectives, use [simple-experiment-design.md](simple-experiment-design.md)
as the default design and evidence handoff, including paper-protocol extraction,
claim coverage and actual CPU/GPU calibration. Its applicable requirements feed
the next useful task; they are not a prerequisite for doing repairs or reading.
Use [simple-collaboration.md](simple-collaboration.md) for native subagents when
independent work benefits from parallelism. Several workers may share one idea;
one coordinator owns journal mutations, accepted handoffs, budget and integration.

## A small project checkpoint

Keep a goal, one idea ID and revision, the present uncertainty, actual artifacts,
the next action, available resources and cumulative usage. Also retain earlier
negative results and any pending run identity. Reuse the user's existing project;
there is no mandatory directory migration or candidate pool.
When delegating, also retain per-assignment input/version bindings, exclusive write
scopes, native identities, partial work and accepted dependencies. Keep these
records separate from runner task JSON and from the journal's global wait state.

The goal is the user's overall objective, not a shorthand for the current task.
Persist the runner's goal contract and completion criteria separately from the
current question. A request to research a direction includes the research work
after feasibility; one active hypothesis does not mean one total iteration.
Preflight, a batch finishing, a report and an individual hypothesis ending are
milestones within that objective. Continue into the next useful action while
scope and resources permit. Only an evidence-backed objective-level conclusion
completes a bounded goal; user stop, resource limits and genuine blocking are
separate statuses.

An evidence note distinguishes `not_checked`, `pending`, `valid`, `invalid`,
`contradicted` and `unavailable`, with the **specific object and scope** checked.
These notes are not universal permission tokens. `valid` evaluation can produce a
negative scientific result; `invalid` evaluation cannot refute the method.

## Restore the scientific policy as well as the process

Identify three separate facts in the checkpoint: the scientific decision edition
and version, the command executor/source pin, and the wake or scheduling mechanism.
Using a Simple runner does not by itself replace an existing full-edition research
policy. An hourly trigger is a wake opportunity, not a one-batch research limit or
evidence of a resident supervisor. Record observed versions; do not infer adoption
from a plugin's display name or a recently installed file.

When the user has authorized a project to adopt Simple, append a versioned policy
change at a reconciled quiet boundary: old/new guidance identities, authority,
changed decision rules and next action. Preserve hypotheses, frozen plans and
exposure, failures, evidence, resource revisions, usage and active job identities.
Reassess existing evidence only for affected claims. Do not retrospectively make
old runs satisfy new criteria or reset budgets, and never silently migrate a live
full-runtime database into the Simple format. Source adoption and goal revision
use their existing interfaces; other policy notes are checkpoint records, not new
runner fields. A material unresolved policy conflict holds only its dependent
decision; independent authorized reading or repair continues. Updating this skill
alone neither migrates a project nor overrides its pause or user stop.

## Stage contracts and connections

Stages are places to work, not a mandatory linear checklist. Existing code can
start at a diagnostic; a mathematical flaw can return directly to derivation.
Independent source/math work and disjoint implementation may overlap when their
inputs are ready. Review consumes the actual available artifact revision. The
coordinator integrates each accepted result and continues ready work without a
blanket wait for every worker; a failed branch blocks only its own dependants.

| Phase | Do the work | Handoff | If it fails or is unknown |
| --- | --- | --- | --- |
| `inspect` | Read the method, logs, goal, resources and pending runs | One uncertainty, current artifacts | `sources`, resource action or `reconcile` |
| `sources` | Read primary papers, experimental sections, appendices and author/baseline code | Located design facts, closest-work gap, inherited choices and justified adaptations | Different source/query, or `analysis` |
| `math` | Check the consequential derivation and assumptions | Conditional prediction and falsifier | Repair math or revise idea |
| `code` | Implement/repair method, baseline and interfaces | Runnable revision and specific checks | Repair code; `math` if construction is wrong |
| `design` | Map claims to required comparisons, predictions, fairness, statistics and measured cost | Versioned experiment matrix, confirmation/exposure record, task/output/analysis mapping and deferred work | `sources`, `evaluator` or resource adjustment |
| `evaluator` | Implement/check the defined metric and aggregation | Qualification evidence and its scope | Repair evaluator or resolve ambiguity |
| `diagnostic` | Check implementation, numerics and resources | Actual outputs and failure localization | `code`, `evaluator` or resource adjustment |
| `experiment` | Run the bounded native-data comparison | Raw outputs, source identities, usage | Reconcile uncertain launch; otherwise classify feedback |
| `verify` | Compare actual arm/run inventory with the pinned plan; inspect fairness, analysis and interpretation | Raw-to-table evidence, missing comparisons, scoped conclusions and next actions | Repair affected layer or `analysis` |
| `analysis` | Interpret evidence; choose a meaningful revision | Reason and explicit next phase/action | Read, derive, code, redesign or retire this idea |
| `delivery` | Report what was learned and changed | Scoped outcome, evidence and open next step | Return to the affected phase for stale evidence |

Before dispatch, ask only whether **this action** has what it needs. A metric
repair requires the definition and a way to test it, not an already-qualified
metric. A diagnostic may expose an unknown baseline or protocol. Mark that scope
and withhold conclusions that depend on unresolved evaluation. Do not convert
every check into an all-project stop condition.

## Choose the experiment that can change the decision

For the next bounded action, state the unresolved question, competing explanations,
which outcomes would change the next step, and its estimated cost. Prefer a cheap
discriminating check to expanding a grid that cannot resolve the current issue.
Batch numbers, card counts, agent counts and repeated positive pilots are not
selection criteria. Use qualitative priorities when uncertainty prevents a credible
numerical estimate; there is no universal score threshold or new admission gate.

Before substantial investment in a performance claim, inspect a reasonable strong
implementation and simple control, verify the consequential measurement, and
locate the cost being targeted. A measured cost decomposition can bound the value
of a local optimization; label its scale and assumptions, including whether the
algorithm changes other costs. Small-scale evidence does not prove behavior at the
paper's full scale. Scale up a representative calibration when that could reverse
the choice. Necessary numerical or saving repairs retain value even when they do
not improve runtime.

Use independent workers for these ready audits as described in
[simple-collaboration.md](simple-collaboration.md#choose-useful-parallel-work).
Accept their concrete findings incrementally. Missing baseline or metric evidence
creates targeted work and restricts dependent claims; it does not stop exploration
or require every reviewer to finish before any useful action proceeds.

## Code and experimental design belong together

Start with the research claim and the closest published experimental designs,
not an arbitrary runnable command. Follow the default design guide and record
its applicable fields in the plan/results templates. Explain deviations from
published protocols and distinguish reported facts, inference and unknowns.

For the selected uncertainty, specify the method revision, relevant baseline or
simple control, original data version/split, exact metric, varied factor, resource
budget and interpretation of possible outcomes. Predict what result would make
the idea weaker as well as stronger. Use meaningful controls rather than a fixed
quota. Existing valid runs count; do not rerun just to populate a new template.
Keep correctness requirements distinct from performance objectives and
implementation diagnostics. A single noisy slower timing or one permitted
fallback is not automatically algorithmic failure; an explicitly preregistered
universal claim can be refuted by a valid counterexample. Preserve that verdict,
then version any narrower successor rather than weakening the old falsifier.
Predict the quantity needed for the decision: predicting when an event occurs
does not establish that its computational cost is predictable. Check that any
proposed predictor is available cheaply before the action it is meant to improve.

Use a justified native subset or precision for fast diagnosis. Retain randomness,
sample selection and uncertainty. Synthetic fixtures can test formulas and edge
cases, but are labeled unit checks, not replacement benchmark evidence. Only
expand repetitions, datasets and ablations when a remaining uncertainty warrants
them. Freeze separate confirmation before using results for a broad claim; do not
repeatedly tune against an inspected holdout.

Size execution to the resource allocation recorded at project setup, including
its latest authorized updates, and the actual capacity of that execution host.
CPU/RAM/GPU limits are project settings, not constants supplied by this skill.
Restore them on resume and across idea revisions; a local observation must not
overwrite a remote allocation. Bound threads/processes, memory and device placement,
then measure a representative pilot. Do not silently drop a required baseline,
change the scientific task or start a paid backend to make a run fit. A smaller
diagnostic can still answer a narrower question while another requirement waits.
For GPU-capable work, record actual allocated devices/VRAM and their availability
window separately from device visibility and observed free memory. Capture a
bounded local resource probe, then a representative measured pilot on the actual
execution host. Carry raw measurements and the plan hash into task inputs;
recalibrate material model/data/precision changes. Do not infer GPU hours from
an idle utilization reading or treat timeout/concurrency settings as VRAM limits.

## Evaluation without an official scorer

Use an available official scorer and original protocol when applicable. A
faithful replica can be compared against that scorer if it actually exists.
There is also a **published mathematical definition** route:

1. Pin the authentic primary paper/protocol, metric equations, conventions,
   aggregation, preprocessing and original released data/splits.
2. Record a short formula-to-code mapping. Write the reference calculation
   independently of the optimized candidate evaluator; copying the same code
   twice does not give independent support.
3. Check the consequential identities, known cases, aggregation, numerical
   precision and relevant edge cases. Choose tests for the metric's risks rather
   than a mandatory count. Hand calculations can serve as an independent reference
   for a simple metric; more complex metrics need stronger reference evidence.
4. Inspect the implementation and outputs in an independent review pass, ideally
   by a separate reviewer when available. No human approval or separate service
   is inherently required. Record remaining uncertainty honestly if independence
   cannot be obtained; keep diagnostics and repairs moving.
5. Retain the real execution, inputs, results and source identities. Qualify only
   the metric and protocol actually checked. Do not call this official parity.

A genuinely ambiguous primary definition blocks the corresponding comparison
claim. Seek the definition or narrow the claim; code, mathematics and evaluation
diagnostics can continue. Do not fabricate an official output or write a PASS to
satisfy a schema. The old `_native_eval.py` has a different full-edition contract;
it is not the checker for this simple path.

## Feedback routes

Each feedback includes the observed fact, affected object, evidence (or why it is
missing), proposed cause, next action and the change that would make a retry useful.

| Feedback | Response |
| --- | --- |
| Missing evidence/source | Produce or retrieve that evidence; use a different query if needed |
| Mathematical error | Repair assumptions/derivation before relying on its prediction |
| Implementation error | Localize, patch and rerun the affected check |
| Evaluation error | Fix definitions/metric code; re-evaluate preserved predictions when valid |
| Valid negative result | Interpret the mechanism; revise the idea, design or scope |
| Insufficient precision/control | Improve the discriminating experiment, not just retry unchanged |
| Resource issue | Optimize, reduce diagnostic scope, choose an authorized host or wait |
| Transient infrastructure error | Inspect the cause and use a bounded retry |
| Active job | Wait on its actual identity and completion condition |
| Unknown launch state | Reconcile that same job before retrying or replacing it; independent tasks may continue |

A result reviewer checks evidence; the controller chooses work; the execution
harness runs bounded commands and preserves identities/logs. Do not expect an
execution driver to invent scientific repairs. The current host can fill these
roles explicitly without installing three separate services.

For an invalid evaluator, identify affected runs, derived tables and conclusions;
mark those claims invalid pending repair, retaining the original artifacts. Reuse
raw outputs only if their provenance and contents support the corrected metric;
rerun only when needed. Unaffected evidence stays usable. Report a repaired
measurement as a correction, not an extra positive research cycle or refutation.

After repeated failures on one issue, change strategy in `analysis`: inspect a
different cause, simplify construction or retire the current idea with its
evidence retained. A new label, new session or repeated identical observation
does not reset effort. Replace an idea only after explicit retirement/completion;
keep one active idea and cumulative project usage.
Tie repeated repairs to the underlying cause across renamed tasks and revisions.
After the retained bound, use a distinct diagnostic or retire the mechanism when
the evidence warrants it; do not spend the next batch on the same unchanged cause.

## Durable journal interface

`scripts/simple_loop.py` is a stdlib SQLite **observation and routing helper**.
The default state belongs under the project `.research-autopilot/` directory.
The descriptor-based evidence reader targets POSIX hosts (Linux/macOS); Windows
execution is not qualified. Use the ordinary checkpoint fallback on other hosts.
It never launches commands, bills providers, authenticates reviewers or grants
scientific approval. The execution companion `simple_runner.py` owns commands,
receipts, task dependencies and decision requests. See
[simple-runner.md](simple-runner.md) for startup and continuation. If no resident
host exists, ending the conversation does not continue computation.

```bash
python3 SKILL_ROOT/scripts/simple_loop.py --root PROJECT init --idea method-a --goal 'Resolve the observed numerical instability'
python3 SKILL_ROOT/scripts/simple_loop.py --root PROJECT status
python3 SKILL_ROOT/scripts/simple_loop.py --root PROJECT record --event feedback.json --expected-version N
```

Substitute actual paths and the observed current version; do not copy a success
record without doing the work. A feedback JSON can start with:

```json
{
  "event_id": "method-a-error-001",
  "kind": "implementation_error",
  "reason": "The current run divides by a zero norm; inspect the normalization and add a numerical diagnostic.",
  "issue": "zero-norm-normalization"
}
```

Attach real `evidence: [{"path": "logs/run-001.txt", "sha256": "ACTUAL_SHA256"}]`
when available. Paths are project relative and verified against their hashes;
evidence symlinks are rejected, including links to files inside the project.
the placeholder above is not valid evidence. Keep versioned evidence files rather
than overwriting what an old event references. `status` is an observation, not a
fresh hash qualification of every historical claim; review current evidence again
before consuming it for a new conclusion.

Events have `event_id`, `kind`, `reason`; usage can report nonnegative
`cpu_seconds`, `wall_seconds`, `tokens`, `cost_micro_usd`. Mutations use an expected
version. Usage values are newly observed increments for this event, not a repeated
copy of the provider's cumulative total. Derive the increment from retained prior
observations so reconciliation cannot double-count yesterday's usage.
An identical event ID and payload is idempotent; conflicting reuse and
stale writes are rejected. Cumulative accounting records observations, not a
substitute for actual host-side limits.

| Event kind | Additional fields / effect |
| --- | --- |
| `progress` | Current `evidence`, explicit `next_phase` |
| `milestone` | Current `evidence`, a `label` and `next_phase`; records preflight/intermediate work without closing the idea |
| `research_cycle` | Current `evidence`, `hypothesis`, `prediction`, `result`, `interpretation`, `next_action`; runner binds the current `goal_contract_version`; records a reported hypothesis-to-decision chain, not a seed/run count |
| `execution_receipt` | Internal, runner-generated command evidence/usage, not an adapter `respond.events` entry; may be recorded after idea closure without changing its scientific state |
| `missing_evidence` | `issue`; optional `target_phase`, default `evaluator` |
| `source_gap`, `mathematical_error`, `implementation_error`, `evaluation_error`, `insufficient_precision`, `resource_issue`, `transient_failure` | `issue`; route to affected work; optional `change_evidence` for an actual changed cause |
| `valid_negative_result` | Current `evidence`; route to `analysis` |
| `wait` | External `identity`, concrete `condition` |
| `wake` | Matching `identity`, current `evidence` of the condition |
| `uncertain_launch` | Actual launch `identity`; require reconciliation |
| `reconcile` | Matching `identity`, `evidence`, `resolution`: `completed`, `failed`, `not_started`, `running` or `unknown` |
| `revision` | Current `evidence`; optional `next_phase` (default `math`); retain lineage and counters |
| `retire_idea` | Explicit reason; archive this idea |
| `replace_idea` | Different `idea`, only after retirement/completion |
| `completion` | Current `evidence`, `outcome`: `supported`, `not_supported`, `inconclusive` or `repaired` |
| `budget_change` | Explicit increased finite `limits` and reason within user authority |

`completion` closes the current idea, including outcome `repaired`. For an
intermediate bug fix while improving the same idea, use `progress` or `revision`
and report the repair's limited scope. Do not close and replace an idea just to
record a successful diagnostic.

The runner's whole-goal closure additionally checks its declared goal contract
and criterion-by-criterion assessment. An idea closing alone leaves the overall
goal active and creates further decision work. Choose a successor after explicit
retirement/completion when justified; if the closure itself was mistaken, use
`revise-goal --reopen` to append that correction and advance the same idea's
revision. Never reset its history, attempts, source pins or deadline.

The legacy `counters.iterations` field counts work observations; it must not be
reported as full scientific cycles. Use explicit research-cycle records for that
reported count, and distinguish them from actual command attempts. Neither count
certifies scientific quality. Three seeds for each of three methods can belong
to one comparison and may still constitute only feasibility work.

An uncertain launch reconciled as `running` retains its identity and wait. When
terminal evidence arrives, send another `reconcile` for that identity. Generic
`wake` clears an ordinary wait, not an unresolved launch.

New journals have no implicit observation-count cap. An explicitly configured
iteration cap, including an existing project's old cap, is retained. The default
3 consecutive repairs per issue routes repeated failures to analysis and a change
of strategy. Runner attempts, reserved command seconds and deadline are separate
finite execution limits; observations do not grant new resources. An agent must
not expand a user's budget through a journal event. Waiting/waking/reconciliation
does not itself consume a work iteration. A different issue name alone is not
meaningful new evidence.

## Host continuation and optional components

Within the active authorized session, continue the next useful task. For external
waiting, retain identity and release the worker when no independent useful work
is ready. New independent observations can resume sources, math, code, design,
evaluation or analysis while retaining that wait. They cannot clear its identity,
launch a replacement experiment or finalize the idea; only the matching
evidence-backed wake clears an ordinary wait. A configured resident supervisor
can wake from job completion, a file/queue event or a scheduled observation; do not
call a model repeatedly to ask whether a run has finished. Preserve run identity
and budget through restart; unknown launch state requires reconciliation.
An hourly wake checks this state and continues eligible work during its active
session; do not voluntarily wait for the next hour after completing one batch.
Recover incrementally from the last accepted checkpoint and observation sequence,
current policy/resource versions, new receipts and unresolved dependencies. Read
older material when a changed claim or recovery question needs it, rather than
repeating a full paper/history audit on every wake. Preserve the underlying archive.

Record command CPU and wall time separately from scheduling/wake delay, model
reasoning, review and integration latency where observable. Parallel command times
must not be summed and called elapsed project time. Native tokens/cost and missing
intervals remain explicitly unknown; command CPU alone cannot establish total
research cost, continuous utilization or a parallel speedup. Keep this telemetry
in linked project notes using actual clocks and measurement scopes, without
inventing unsupported runner accounting fields.

Start the bundled `simple_runner.py run` supervisor for actual execution and
watched waits. Its per-task lifecycle is separate from the journal's global
`wait` and `uncertain_launch` records: do not record every parallel task as a
global journal wait. The active Work agent handles its decision inbox; a configured
agent command can use the same protocol for unattended continuation on a live host.
The supervisor survives ordinary idle/decision waits, but installation does not
launch it and it cannot resurrect a destroyed platform host. Hermes/ACP, SSH and
the full runtime are optional integrations. The old controller admission and
full autonomy planner retain their original contract; do not call them expecting
to consume a simple journal.

For a dashboard, the optional `research_progress.py` observer accepts edition
`rsi-simple` and manually recorded stage/status observations. It does not read the
simple SQLite journal automatically. Report only visible work, with no invented
percentage, future execution or success. Keep task state private unless the user
has authorized a delivery destination.
