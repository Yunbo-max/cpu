## Metric and encoding review

- `evaluate_pilot.py:9–13`: pairwise Gini denominator is correct: `2*L*sum(costs)`. The sorted form is algebraically equivalent. `34–39` checks four analytic examples including equal costs and finite-L extreme inequality and rejects the zero-total vector. `51–53` computes each language's mean over the SAME row objects and applies Gini to these means, with a sorted-form check for each actual aggregate. This implements the intended primary estimand.
- `53`: mean sentence-level Gini is separately named, not substituted for primary Gini. Worst language, its mean cost, and sum of language means are retained. The latter is not literally total corpus tokens, but total can be recovered as N times this quantity. Descriptive comparisons must use the primary field consistently.
- `14–21`: vocabulary begins with all 256 byte symbols, assigns unique IDs only to new merged strings, and sets `t.pre_tokenizer=pre` directly on the backend. No special tokens or postprocessor are installed; raw Tokenizers encoding therefore has no automatically added framing tokens in this construction. Keeping sorted alphabet IDs affects token IDs rather than the token-string/count comparison.
- `22–33`: the reference encoder independently replays each merge once in order, left-to-right with nonoverlap, inside each shared pretoken. That is the intended native sequential-merge semantics. It shares pretokenization with the backend, so it verifies the merge engine rather than independently validating preprocessing. `44–49` checks exact token strings for Unicode, repetition, empty/whitespace fixtures and the first eight development rows in both languages: 22 fixtures per arm. The claim should be 'exact agreement on 22 checked fixtures', not exhaustive agreement over every scored text. A disagreement would rightly halt acceptance; a pass does not mathematically prove universal equivalence between implementations.
- `55–56`: equal realized merge and unique-vocabulary checks catch the principal size confound across discovered arms. They do not on their own ensure the frozen target of 1000 merges or all seven arms. A one-arm directory passes these two conditions; an extra stale arm is also included by the glob at `42`. External runner guards now reported by the coordinator reduce practical risk. Separate acceptance should require exact set `{classical, base, window_a1, hybrid500, ratio_equal, ratio_dev, balanced}`, each 1000 merges, equal vocabulary, plus no unplanned outputs.
- Python `assert` statements are the evaluator's validation mechanism. They must execute with optimization disabled. No claim is made here about the submitted command; the coordinator should retain its actual command/environment receipt.

## Split, provenance, and control review

- `prepare_pilot.py:27–36`: deterministic hashing of official TICO stringIDs selects 200 dev and 200 test rows independently, preserves bilingual rows together, enforces 200 unique IDs, rejects empty translations, and checks dev/test ID disjointness. Only selected dev rows are written to native `--dev` files. Ratio calibration at `40–41` also uses only these dev rows. There is no direct TICO-test or Books-to-ratio leakage in this code.
- `40–41`: ratio uses actual initialized byte-mapped pretoken lengths, including the same prefix-space behavior as training; this is more faithful to the native ratio implementation than raw UTF-8 byte length. The frozen plan's French ratio agrees with the value in the inspected manifest. No arithmetic recomputation was performed by this reviewer.
- ID disjointness does not establish text or semantic deduplication, and training-web overlap is not checked here. No leakage is demonstrated. Report this as unverified; a read-only normalized-text overlap audit can later identify exact duplicates without tuning against outcomes. Correlated sources can span official splits (the manifest includes CMU source-group names in both), so later confidence intervals and confirmation policies should consider source clustering.
- `37–39`: Books rows remain paired within each translation object; manifest lists IDs 0 through 99. Code does not itself assert exactly 100 rows, unique Books IDs, or the declared first-contiguous selection; that property currently depends on the acquired evidence. Manifest/output acceptance should check these properties and required en/fr keys. The plan correctly avoids across-book or significance claims. Future unused record IDs from the same book are not automatically independent confirmation titles; obtain actual title/source identity before claiming disjoint books.
- `12–18`: both language training sets are exactly 40 nontruncated documents; Classical concatenation preserves a newline boundary between them. Document counts are balanced already, while observed pretoken counts differ: 21,990 English and 43,971 French. Thus the proposed control should consistently be called balancing pretoken occurrences, not simply balancing document counts.
- `19–24`: the resampled control preserves 65,961 total pretoken occurrences, allocates 32,980/32,981 occurrences across the two languages, and samples using a declared seed. Its dictionary preserves pretoken strings and counts for the native dict-input learner. This fixes a meaningful budget unit but not total bytes or pair opportunities. One multinomial resample changes empirical within-language frequencies and can drop rare items; its contrast combines language reweighting and resampling noise. It is a legitimate declared pilot control, not a clean deterministic isolation of weighting alone. Later mechanisms should include deterministic frequency weighting or repeated sampling where resource budgets allow.
- Plan information permissions are candid: base/window/hybrid/ratio_dev consume dev information; Classical/equal-ratio/balanced do not. This supports the declared method comparison, but not claims that any advantage is solely due to a superior objective under identical supervision. Matched informative baselines, pooled-domain and domain-swap controls remain necessary for a future improved-method claim, as the plan itself records.
- `prepare_pilot.py:42–43`: prepared-file hashes are recorded, but the evaluator never verifies them or attaches manifest row IDs beside costs. Row order permits reconstruction from the pinned data. A separate acceptance receipt should bind evaluated source/data/output hashes and verify ordered split IDs. If preparation is rerun in a nonempty data directory, line 42 will also hash an old `manifest.json` before overwriting it, producing a stale self-entry. The current inspected manifest has no such entry; avoid rerunning this frozen preparation or explicitly exclude the manifest in a separately versioned script.
- The inspected manifest names licenses and IDs but does not itself contain complete upstream URLs, revisions, or retrieval receipts. Such evidence may exist elsewhere under the coordinator's acquisition records; this review did not inspect it. Preserve those references rather than treating prepared-file hashes alone as full provenance.
